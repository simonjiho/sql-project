## 데이터 배경 (검산 기준값)

| 테이블 | 내용 | 기대 건수 |
|---|---|---|
| student | 학생. major 5종 + HR(981~1000) | 1,000 |
| enroll | 수강. 학생당 0~2건 규칙 + 고아 수강 2건(1001, 1010) | 규칙 기반 검산 |
| customers | 고객 | 500 |
| orders | 고객 1명당 정확히 6건 | 3,000 |
| emp | CEO 1 + 매니저 10 + 직원 300 (3단계 계층) | 311 |

- 수강 없음: student_id % 3 = 0 → 약 333명 (Anti-Join 검산에 사용)
- 고아 수강 2건은 RIGHT/FULL JOIN 결과 검산에 사용

### ⚠️ 실측 데이터와 슬라이드 배경의 불일치 (0단계에서 확인)

슬라이드 배경은 "student_id % 3 규칙, 학생당 0~2건"이라고 설명하지만, 제공된 스크립트가 실제로 적재하는 규칙은 다르다:

| 규칙 | 학생 수 | 수강 건수 |
|---|---|---|
| student_id % 10 = 0 | 100명 | 0건 |
| 짝수(단, %10≠0) | 400명 | 2건 |
| 홀수 | 500명 | 3건 |

→ enroll 총 2,302건(정규 2,300 + 고아 2). **검산은 실측 기준(수강 없는 학생 100명)으로 수행**하고, 제출 보고 시 슬라이드 배경과 다름을 언급할 수 있게 기록해둔다.

emp도 마찬가지로 불일치: 슬라이드는 "각 직원은 매니저 10명 중 1명에게 배정"(depth 1/10/300)이라 하지만, 적재 수식이 `manager_id = 1+((gs-1)%10)`이어서 **Dev 30명이 CEO 직속, Mgr_11은 부하 0명** (실측 depth 0:1 / 1:40 / 2:270). 문항 22 결과 해석 시 언급.

## 진행 원칙 (실습1과 동일)

- 각 단계의 작업계획을 먼저 제시하고 사용자 승인 후 작업한다.
- 각 단계 결과물을 사용자 검토 승인 후 다음 단계로 이동한다.
- 모든 쿼리는 결과 행 수·합계 검산과 함께 제시한다.
- 채점 기준에 맞춰 SELECT에는 문항이 요구한 컬럼만 포함한다.

## 문항별 주의사항 메모

- 채점에서 "불필요한 컬럼 선택"을 확인하므로 `SELECT *` 금지, 요구 컬럼만 조회.
- 문항 3·4: PostgreSQL은 RIGHT/FULL JOIN을 직접 지원. 고아 수강 2건이 결과에 나타나는지 확인.
- 문항 5·18, 6·17: JOIN 관점(1단계)과 서브쿼리 관점(2단계)으로 같은 결과를 다른 문법으로 작성 — 두 방식 행 수 일치 검산.
- 문항 8: 슬라이드 공통 주석은 `LIMIT 5`이나 문항 지문은 상위 10명 → LIMIT 10 적용, 필요 시 동점 처리 언급.
- 문항 12: course_owner는 lab 스키마에 생성, 매니저는 이름이 'Mgr_'로 시작하는 10명에서 임의 매핑.
- 문항 13: CROSS JOIN 폭발(1,000 × 20과목) 주의 — LIMIT 100으로 샘플만.
- 문항 21: 소계 행 NULL과 실제 NULL 구분을 위해 GROUPING() 사용, 정렬식으로 소계를 하단 배치.
- 문항 24: enroll에 시간 컬럼이 없어 ORDER BY course 기준(지문 명시)으로 LAG 적용.
- 문항 25: 수정본 PDF(`종합실습2.pdf`, 원본 강의자료 214~224페이지에 반영 완료)에서 문제가 교체됨 — 기존 23번 중복 지문이 아니라 orders 누적합·이동평균 문제. 지문의 "초음하는"은 "초과하는"의 오타로 해석. 50% 초과 첫 order_id는 누적합 CTE + WHERE로 조회.
- 문항 23: 서브쿼리 방식과 CTE 방식 모두 작성 필요.
