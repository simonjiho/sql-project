## 2. 작업계획

1. 요구사항과 관리자 답변을 업무 영역별로 ERD 구성요소에 대응한다.
2. 정제된 엔터티·속성과 DBML·DDL의 테이블 및 컬럼을 비교한다.
3. 4·5단계 관계 ID와 DDL 외래키를 비교한다.
4. 업무 규칙을 DDL 직접 제약, 트랜잭션 절차, 권한, 조회 계산으로 구분한다.
5. 구조 정합성과 실행 안전성 기준을 확인한다.
6. 빈 PostgreSQL 환경에서 DDL 실행과 구조 검증 SQL을 수행한다.

## 5. 데이터 무결성 보장 수준

### 5.1 DDL이 직접 보장하는 규칙

- 18개 테이블의 내부 PK와 필수 속성 `NOT NULL`
- 학과 코드, 학번, 교번, 교과목 코드 및 영역별 이메일 유일성
- 학과명 대소문자 무시 유일성
- 교과목·연도·학기·분반 및 학생·강좌 조합 유일성
- 학년, 학점, 연도, 학기, 정원과 순번 범위
- 학적·재직·개설·수강·성적·승인·실행 상태의 허용값
- 수강 상태와 취소 시각, 성적과 성적 변경 시각의 동시 존재 규칙
- 등록·변경·삭제별 before/after 스냅샷 존재 규칙
- 변경처리 내 기록 순번, `changed_columns` 중복·빈 문자열 금지 및 변경분류 중복 금지
- 감사 조회 성공·실패별 결과 건수와 오류 설명 조건
- 역할·정책·보류·폐기 기간의 기본 시각 순서
- 모든 물리 FK의 DELETE/UPDATE RESTRICT

### 5.2 전용 프로시저 또는 트랜잭션이 필요한 규칙

| 업무 규칙 | 필요한 구현 |
|---|---|
| 재학 학생만 수강신청 | 신청 프로시저에서 학생 행 잠금 후 상태 확인 |
| 모집 중 강좌와 잔여석 확인 | 강좌 행 잠금 또는 원자적 조건 UPDATE로 정원 초과 경쟁 차단 |
| 퇴직 교수에게 신규 강좌 배정 금지 | 강좌 개설 프로시저에서 교수 상태 확인 |
| 수강 발생 후 담당 교수 변경 금지 | 강좌 수정 프로시저에서 수강 존재 여부 확인 |
| 성적 있는 수강 취소·강좌 폐강 금지 | 취소·폐강 프로시저에서 성적 존재 여부 확인 |
| 폐강과 신청 완료 수강 일괄 취소 | 한 변경처리와 단일 DB 트랜잭션으로 처리 |
| 담당 교수만 성적 입력·정정 | 강좌 담당자와 실행 행위자 비교 |
| 승인자 역할·자기 승인 금지 | 승인 시 유효 역할 및 요청자 불일치 검사 |
| 오래된 요청 적용 금지 | 대상 현재 버전과 `target_version_snapshot` 비교 |
| 학사 변경과 감사기록 원자성 | 학사 DML과 변경처리·기록·분류를 같은 트랜잭션에서 생성 |
| 부모 기준 최소 카디널리티 | 행위자-역할, 처리-기록, UPDATE 변경 컬럼 배열, 기록-분류를 커밋 전 검사 |
| JSONB 스냅샷 구조 | 대상 유형·스키마 버전별 생성 함수 또는 JSON Schema 검사 |
| 보존기간·활성 보류·승인 확인 | 폐기 전용 프로시저에서 세 조건을 함께 확인 |

### 5.3 권한으로 보장할 규칙

- 애플리케이션 일반 역할에 `audit` 테이블 직접 UPDATE/DELETE 권한을 부여하지 않는다.
- 학사 담당자·교수에게 감사 원본 전체 조회 권한을 부여하지 않는다.
- 감사 조회는 조회 목적을 받는 전용 함수나 API를 통해 수행하고 `AuditAccessLog`를 같은 업무에서 생성한다.
- 감사 원본 오류는 UPDATE가 아니라 `AuditCorrection` INSERT만 허용한다.
- 폐기는 승인된 전용 함수에만 필요한 제한 권한을 부여한다.

### 5.4 조회에서 계산할 항목

- 전화번호가 NULL이면 `미등록`
- 학년 1은 `신입생`, 2·3은 `재학생`, 4는 `졸업반`
- 입학일에서 입학 연도 추출
- 신청 완료 수강만 강좌 수강 인원에 포함
- 성적이 NULL이면 `미정`
- 정원에서 현재 신청 완료 인원을 뺀 잔여석
- 해제 시각이 없는 보존보류의 활성 여부

| 본 문서 | 요구사항 대응과 보장 수준 명시 | ERD가 표현하는 구조와 후속 구현 책임을 구분 |

엔터티·속성·관계·카디널리티, DBML과 DDL은 동일한 최종 모델을 표현하며 문서 간 구조 불일치가 없다.

## 7. 의도적으로 유지한 설계

- 감사 전후값과 다형 범위는 JSONB 스냅샷으로 유지한다.
- 현재 학사 대상과 감사 스냅샷 사이에는 물리 FK를 두지 않는다.
- 학생·교수와 업무행위자 사이에도 학사 FK를 두지 않는다.
- 감사 조회 결과 행과 조회기록, 폐기실행과 삭제 대상에도 FK를 두지 않는다.
- FK만으로 표현할 수 없는 부모 기준 최소 1건은 프로시저 규칙으로 유지한다.
- 감사 폐기를 위해 일반 CASCADE를 사용하지 않고 자식부터 처리하는 전용 절차를 사용한다.

이는 누락이 아니라 학사 삭제와 감사 보존의 생명주기를 분리하기 위한 결정이다.
