## 2. 작업계획

1. 엔터티별 후보키와 주요 함수 종속성을 정리한다.
2. 반복 그룹과 비원자 속성을 기준으로 제1정규형을 검토한다.
3. 복합 후보키의 부분 함수 종속성을 기준으로 제2정규형을 검토한다.
4. 비키 속성 사이의 이행 함수 종속성을 기준으로 제3정규형을 검토한다.
5. 감사 스냅샷, JSONB, 배열과 검색용 중복 컬럼의 유지 필요성을 검토한다.
6. 정규화 위반과 의도적 비정규화를 구분하고 수정 영향 범위를 작성한다.

## 3. 판정 기준

### 3.1 제1정규형(1NF)

- 한 컬럼에는 한 의미의 원자값만 저장한다.
- 같은 종류의 값이 한 행 안에서 배열이나 반복 컬럼으로 늘어나지 않는다.
- 행은 PK 또는 후보키로 유일하게 식별할 수 있다.

### 3.2 제2정규형(2NF)

- 1NF를 만족한다.
- 복합 후보키가 있는 경우 모든 비키 속성이 후보키 전체에 완전 함수 종속된다.

### 3.3 제3정규형(3NF)

- 2NF를 만족한다.
- 비키 속성이 다른 비키 속성을 거쳐 후보키에 이행 함수 종속되지 않는다.
- 다른 엔터티에서 관리할 현재 설명값을 중복 저장하지 않는다.

감사 시점의 사실을 보존하기 위한 스냅샷은 현재 마스터 데이터의 단순 복사와 다르다. 현재값이 아니라 **사건 발생 당시 값**이라는 독립 업무 사실이면 의도적 비정규화로 분류할 수 있다.

## 4. 후보키와 함수 종속성

### 4.1 학사관리 영역

| 엔터티 | 후보키 | 주요 함수 종속성 | 판정 |
|---|---|---|---|
| 학과 | `department_id`, `department_code`, 정규화된 `department_name` | 각 후보키 → 학과의 모든 속성 | 3NF |
| 학생 | `student_id`, `student_number`, 정규화된 `email` | 각 후보키 → 학생의 모든 속성 | 3NF |
| 교수 | `professor_id`, `employee_number`, 정규화된 `email` | 각 후보키 → 교수의 모든 속성 | 3NF |
| 교과목 | `subject_id`, `subject_code` | 각 후보키 → 교과목의 모든 속성 | 3NF |
| 강좌 | `class_id`, (`subject_id`, `opening_year`, `semester`, `section`) | 각 후보키 → 담당 교수·정원·상태·시각 | 3NF |
| 수강 | `enrollment_id`, (`student_id`, `class_id`) | 각 후보키 → 상태·신청/취소 시각·성적 | 3NF |

학과명과 이메일의 후보키 판단은 입력 정규화 후 적용되는 유일 제약을 전제로 한다. 학사 영역에는 학과명, 교수명, 교과목명처럼 다른 엔터티에서 얻을 수 있는 설명값을 FK 옆에 중복 저장하지 않는다.

### 4.2 변경이력·감사 영역

| 엔터티 | 후보키 | 주요 함수 종속성 | 판정 |
|---|---|---|---|
| 업무행위자 | `actor_id`, `actor_code` | 각 후보키 → 행위자 현재 속성 | 3NF |
| 행위자역할 | `actor_role_id`, (`actor_id`, `role_code`, `valid_from`) | 역할 이력 키 전체 → 종료 시각 | 3NF |
| 변경요청 | `change_request_id` | 요청 ID → 대상·스냅샷·사유·상태·시각 | JSONB 예외를 제외하면 3NF |
| 변경승인 | `change_approval_id`, `change_request_id` | 요청 ID → 승인자·판단·시각 | 3NF |
| 변경처리 | `change_operation_id`, nullable 유일 `change_request_id` | 처리 ID → 행위자·출처·사유·시각 | 스냅샷 중복을 제외하면 3NF |
| 변경기록 | `change_record_id`, (`change_operation_id`, `record_sequence`) | 기록 키 전체 → 대상·전후값·검색 태그 | 배열 수정 필요 |
| 감사조회기록 | `access_log_id` | 조회 ID → 조회자·목적·조건·결과 | JSONB 예외를 제외하면 3NF |
| 감사보정기록 | `audit_correction_id` | 보정 ID → 원본 논리키·사유·설명·처리자 | 3NF |
| 보존정책 | `retention_policy_id`, (`policy_code`, `version_number`) | 정책 버전 키 전체 → 범위·기간·승인정보 | JSONB 예외를 제외하면 3NF |
| 보존보류 | `retention_hold_id` | 보류 ID → 대상범위·사유·설정/해제정보 | JSONB 예외를 제외하면 3NF |
| 폐기실행 | `disposal_execution_id` | 실행 ID → 정책·대상범위·승인/실행결과 | JSONB 예외를 제외하면 3NF |

감사 영역의 행위자 코드·표시명 스냅샷은 같은 `actor_id`라도 사건 시점에 따라 표시명이 달라질 수 있으므로 현재 행위자 속성에 대한 단순 이행 종속으로 보지 않는다. 다만 구조가 항상 코드와 이름으로 고정된 스냅샷은 JSONB가 아니라 원자 컬럼으로 저장한다.

## 5. 제1정규형 검토

### 5.1 수정이 필요한 항목

| 대상 | 현재 구조 | 문제 | 수정안 |
|---|---|---|---|
| 변경기록의 실제 변경 항목 | `changed_columns TEXT[]` | 한 행에 여러 컬럼명이 반복되는 다중값 속성 | `ChangeRecordColumn` 자식 엔터티로 분리 |
| 변경기록의 감사 분류 | `change_categories TEXT[]` | 한 행에 여러 분류가 반복되는 다중값 속성 | `ChangeRecordCategory` 자식 엔터티로 분리 |
| 강좌 검색 태그 | `class_key_tag VARCHAR(100)` | 교과목 코드·연도·학기·분반을 한 문자열로 결합 | `subject_code_tag`, `opening_year_tag`, `semester_tag`, `section_tag`로 분해 |
| 구조가 고정된 행위자 스냅샷 | 여러 `*_snapshot JSONB` | 코드와 표시명이라는 고정 구조를 JSON으로 저장 | `*_code_snapshot`, `*_name_snapshot` 원자 컬럼으로 분해 |

### 5.2 추가되는 엔터티

#### 변경항목(ChangeRecordColumn)

- **발생 단위**: 한 변경기록에서 실제로 달라진 컬럼 하나당 한 건.
- **후보키**: `change_record_column_id`, (`change_record_id`, `column_name`).
- **속성**: 내부 PK, 변경기록 REF, 컬럼명, 표시 순서.
- **업무 규칙**: UPDATE 변경기록에는 최소 한 건이 필요하고 CREATE·DELETE에는 선택적으로 전체 대상 컬럼을 기록할 수 있다.

#### 변경분류(ChangeRecordCategory)

- **발생 단위**: 한 변경기록에 부여된 감사 분류 하나당 한 건.
- **후보키**: `change_record_category_id`, (`change_record_id`, `category_code`).
- **속성**: 내부 PK, 변경기록 REF, 분류 코드.
- **업무 규칙**: 모든 변경기록에는 최소 한 건이 필요하며 수강 상태와 성적이 함께 변경되면 복수 분류를 가질 수 있다.

### 5.3 1NF 판정

- 위 두 배열과 복합 문자열을 수정하면 일반 관계형 속성은 1NF를 만족한다.
- JSONB 스냅샷은 8절의 의도적 비정규화 예외로 관리한다.

## 6. 제2정규형 검토

복합 후보키가 있는 엔터티를 집중 검토했다.

| 엔터티 | 복합 후보키 | 부분 종속 검토 | 판정 |
|---|---|---|---|
| 강좌 | 교과목+연도+학기+분반 | 담당 교수·정원·상태는 조합 전체로 특정됨 | 통과 |
| 수강 | 학생+강좌 | 상태·시각·성적은 두 값의 조합으로 특정됨 | 통과 |
| 행위자역할 | 행위자+역할+시작 시각 | 종료 시각은 특정 역할 기간 전체에 종속 | 통과 |
| 변경기록 | 변경처리+처리 내 순번 | 대상·스냅샷은 두 값의 조합으로 특정됨 | 통과 |
| 보존정책 | 정책 코드+버전 | 이름·범위·기간·승인정보는 정책 버전 전체에 종속 | 통과 |
| 변경항목 | 변경기록+컬럼명 | 표시 순서는 조합 전체에 종속 | 통과 |
| 변경분류 | 변경기록+분류코드 | 별도 비키 속성이 없거나 조합 전체에 종속 | 통과 |

`record_sequence`와 `version_number`는 단독 후보키가 아니다. 정규화 반영 엔터티·속성 문서에서 각각 복합 AK의 일부로 표기를 바로잡는다.

## 7. 제3정규형 검토

### 7.1 통과 항목

- 학생과 교수는 학과명을 저장하지 않고 학과 참조만 보유한다.
- 강좌는 교과목명과 교수명을 저장하지 않고 각 참조만 보유한다.
- 수강은 학생 이름, 강좌명, 수강 인원을 저장하지 않는다.
- 변경승인·변경처리·조회기록은 행위자 현재 이름을 대신하지 않고 사건 당시 표시값을 별도 사실로 저장한다.
- 파생 표시값인 미등록, 학년 안내, 입학 연도, 미정, 수강 인원과 잔여석은 저장하지 않는다.

### 7.2 의도적인 중복 속성

| 속성 | 원래 값과의 관계 | 유지 이유 | 일관성 보장 |
|---|---|---|---|
| 행위자 코드·표시명 스냅샷 | 현재 `AuditActor`와 일부 중복 | 이름 변경 후에도 사건 당시 표시를 재구성 | 사건 생성 프로시저에서만 복사, 이후 수정 금지 |
| `student_number_tag` | 업무키 스냅샷에서 추출 가능 | 학생 타임라인 조회용 정형 인덱스 | 스냅샷 생성 함수에서 동시 생성 |
| 강좌 검색 태그 4개 | 업무키 스냅샷에서 추출 가능 | 강좌 타임라인의 정형 복합 인덱스 | 스냅샷 생성 함수에서 동시 생성 |
| `is_important` | 변경분류와 전후값에서 판정 가능 | 중요 변경 기간 조회의 헤더 필터 | 같은 트랜잭션에서 분류·전후값과 교차 검증 |
| `deleted_record_count` | 폐기 결과 JSON에서 계산 가능 | 실행 결과 집계와 검증 편의 | 결과 JSON에는 건수를 중복 기록하지 않음 |

위 속성은 키에 직접 종속되고 요구되는 과거 재구성·검색·운영 검증 목적이 분명하므로 통제된 비정규화로 유지한다.

### 7.3 3NF 판정

배열 분리, 복합키 표기 수정과 고정 구조 JSON 분해 후 일반 관계형 부분은 3NF를 만족한다. 감사 스냅샷과 검색용 중복 속성은 의도적 비정규화로 별도 통제한다.

## 8. JSONB와 다형 구조의 의도적 비정규화

### 8.1 유지할 JSONB

| 속성 | 유지 이유 | 허용 구조 통제 |
|---|---|---|
| 변경요청의 업무키·before·proposed-after | 대상 엔터티마다 속성 구조가 다르고 승인 당시 전체값 고정 필요 | `target_type`, 스키마 버전과 유형별 JSON Schema 검사 |
| 변경기록의 업무키·before·after | 등록·변경·삭제 당시 전체 행 재구성 및 학사 행 삭제 독립성 | 대상 유형별 생성 함수, 스키마 버전, 수정 금지 |
| 감사조회기록의 필터 | 검색 종류마다 조건 조합이 다름 | `target_audit_type`별 허용 키 검사 |
| 보존정책의 적용 범위 | 정책 버전마다 대상 종류와 조건이 다름 | 정책 승인 프로시저에서 범위 구조 검사 |
| 보존보류의 대상 범위 | 학생·강좌·처리·기간 등 다형 범위 | `target_scope_type`별 필수 키 검사 |
| 폐기실행의 대상 범위·결과 | 실행마다 대상과 오류 구조가 달라짐 | 실행 프로시저가 표준 결과 구조 생성 |

### 8.2 JSONB 유지에 따른 제약

- 업무상 자주 검색하는 학번과 강좌키는 JSONB에만 두지 않고 정형 태그 컬럼으로 함께 저장한다.
- 애플리케이션 임의 JSON을 그대로 저장하지 않고 신뢰된 프로시저가 생성하거나 검증한다.
- 모든 전후 스냅샷에는 대상 유형과 스냅샷 구조 버전을 함께 저장한다.
- JSONB 내부 현재 학사정보에 FK를 걸지 않는다.
- 일반 속성으로 안정적으로 정의할 수 있는 행위자 코드·표시명은 JSONB로 저장하지 않는다.

## 9. 비정규화 검토에 전달할 정규화안

### 9.1 엔터티·속성 정규화안

- 감사 엔터티를 11개에서 13개로, 전체 엔터티를 17개에서 19개로 변경한다.
- `ChangeRecordColumn`, `ChangeRecordCategory` 정의와 속성을 추가한다.
- `ChangeRecord.changed_columns`, `ChangeRecord.change_categories`를 제거한다.
- `class_key_tag`를 강좌키의 네 원자 태그로 교체한다.
- 고정 구조의 행위자 JSON 스냅샷을 코드·표시명 컬럼으로 분해한다.
- 변경기록·보존정책 등 복합 후보키 표기를 바로잡는다.

### 9.2 관계 설계 시 검토할 정규화안

- 변경기록-변경항목, 변경기록-변경분류의 물리 관계를 추가한다.
- 감사 물리 관계 수를 17개에서 19개로 변경한다.
- 변경기록-변경항목은 전체 `0..N`, UPDATE일 때 `1..N`으로 정의한다.
- 변경기록-변경분류는 `1..N`으로 정의한다.
- 강좌 검색 논리 관계의 연결 속성을 네 개의 원자 태그로 변경한다.
- 배열 기반 최소 건수 설명을 자식 엔터티 기반 절차 제약으로 변경한다.

## 10. 최종 판정

| 영역 | 1NF | 2NF | 3NF | 비고 |
|---|---|---|---|---|
| 학사관리 6개 엔터티 | 통과 | 통과 | 통과 | 수정 없음 |
| 감사 영역 기존 11개 | 조건부 통과 | 통과 | 조건부 통과 | 배열·고정 구조 JSON·복합키 표기 수정 필요 |
| 감사 영역 수정 후 13개 | 통과 | 통과 | 통과 | 통제된 JSONB·스냅샷 비정규화 유지 |

정규화 수정은 요구사항의 업무 의미를 바꾸지 않는다. 반복값을 자식 엔터티로 분리하고 고정 구조를 원자 컬럼으로 바꾸며, 삭제 독립성과 과거 재구성에 필요한 스냅샷은 유지한다.
