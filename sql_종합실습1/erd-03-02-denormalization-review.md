이 문서는 정규화안이 요구사항과 감사 데이터의 신뢰성을 유지하면서도 불필요한 엔터티·관계·쓰기 비용을 만들지 않는지 검토한다. 정규화 검토와 이 검토의 결론을 종합해 최종 엔터티·속성 기준을 확정한다.

## 2. 검토 목적

1. 업무상 독립성이 없는 값이 별도 엔터티로 과도하게 분리되지 않았는지 확인한다.
2. 조회·감사·보존을 위해 필요한 의도적 중복은 정규화 위반과 구분한다.
3. 비정규화한 값의 원본과 생성 책임을 명확히 한다.
4. 중복값 불일치, 누락 및 임의 입력을 막는 제약과 시험 기준을 정의한다.
5. 실습 범위에서 구현·설명·검증 가능한 수준으로 모델 복잡도를 조정한다.

## 3. 판단 기준

### 3.1 엔터티 분리를 유지하는 기준

다음 중 하나 이상을 만족하면 별도 엔터티를 유지한다.

- 독립적인 발생 시점과 수명주기를 가진 업무 사실이다.
- 한 부모에 여러 건이 반복되며 각 건을 독립적으로 식별·조회해야 한다.
- 자체 속성, 상태 전이, 책임자 또는 보존 규칙을 가진다.
- FK, 유일 제약 또는 카디널리티로 보호해야 하는 독립 관계다.
- 여러 부모가 공동으로 참조하거나 별도 인덱스로 자주 검색하는 대상이다.

### 3.2 비정규화를 허용하는 기준

다음 조건을 모두 만족할 때만 중복·배열·JSONB 저장을 허용한다.

- 요구사항상 과거 시점 재구성, 감사 검색 또는 처리 결과 증빙에 필요하다.
- 원본 데이터와 중복 데이터의 우선순위가 명확하다.
- 일반 사용자가 중복값을 직접 입력하거나 수정할 수 없다.
- 신뢰된 함수 또는 프로시저가 같은 트랜잭션에서 생성한다.
- 불일치 여부를 시험하거나 검증할 수 있다.
- 저장·쓰기 복잡성보다 조회·보존 또는 모델 단순화의 이익이 크다.

### 3.3 과도한 정규화로 판단하는 기준

다음 특징이 중첩되면 별도 엔터티를 축소 후보로 본다.

- 부모 없이는 의미가 없고 독립적인 수명주기도 없다.
- 자체 업무 속성이 거의 없으며 값이 다른 저장값에서 계산 가능하다.
- 해당 자식을 기준으로 한 독립 업무나 권한이 요구되지 않는다.
- 분리 때문에 최소 자식 수 검증, 추가 FK, 추가 인덱스 및 폐기 순서만 늘어난다.
- 배열 또는 계산값으로 표현해도 요구사항과 감사 신뢰성이 약화되지 않는다.

## 5. 과도한 분리 축소 제안

### 5.1 대상: 변경항목(ChangeRecordColumn)

현재 `ChangeRecordColumn`은 다음 값만 가진다.

- 내부 식별자
- 변경기록 참조
- 변경 컬럼명
- 표시 순서

변경 전·후 실제 값은 이미 `ChangeRecord.before_snapshot`과 `ChangeRecord.after_snapshot`에 존재한다. 변경항목은 독립적인 승인, 책임자, 보존기간 또는 상태를 가지지 않으며 항상 부모 변경기록과 함께 생성·조회·폐기된다.

별도 엔터티를 유지하면 다음 비용이 발생한다.

- UPDATE 한 건마다 여러 자식 행을 추가로 생성한다.
- 변경기록당 컬럼명·표시순서 유일 제약이 필요하다.
- UPDATE 기록의 자식 최소 1건을 프로시저에서 검증해야 한다.
- 감사 폐기 시 변경항목을 부모보다 먼저 삭제해야 한다.
- 전후 스냅샷과 변경항목 자식 행의 일치 여부를 별도로 검증해야 한다.

요구사항은 실제로 달라진 항목을 확인할 수 있으면 충족된다. 변경 컬럼 자체에 독립 업무 의미가 있거나 변경 컬럼을 다른 엔터티가 참조해야 한다는 요구는 없다. 따라서 변경항목은 별도 엔터티보다 변경기록의 통제된 다중값 속성으로 관리하는 편이 실습 범위에 적합하다.

### 5.2 변경 후 속성안

`ChangeRecord`에 다음 속성을 둔다.

| 속성 후보 | 업무명 | 구분 | 필수성 | 타입 후보 | 규칙 |
|---|---|---|---|---|---|
| `changed_columns` | 실제 변경 컬럼 목록 | 일반·의도적 비정규화 | 필수 | `TEXT[]` | 시스템 생성, 중복·빈 문자열 금지, 사용자 직접 입력·수정 금지 |

세부 규칙은 다음과 같다.

- `UPDATE`는 `cardinality(changed_columns) >= 1`이어야 한다.
- `CREATE`와 `DELETE`는 빈 배열을 허용한다.
- 배열 순서는 감사 화면의 기본 표시 순서로 사용한다.
- 같은 컬럼명을 배열에 두 번 저장하지 않는다.
- 배열 원소는 대상 스냅샷 스키마에 존재하는 허용 컬럼명이어야 한다.
- 정규화한 업무값이 같은 컬럼은 배열에 포함하지 않는다.
- `before_snapshot`과 `after_snapshot`이 변경 사실의 원본이며 `changed_columns`는 조회·표시용 보조값이다.

### 5.3 생성 및 일관성 보장

`changed_columns`는 애플리케이션이 임의로 전달한 값을 그대로 저장하지 않는다. 감사 생성 함수가 정규화된 전후 스냅샷을 비교하여 생성하고 변경기록과 같은 트랜잭션에서 저장한다.

검증 함수는 다음을 확인한다.

1. UPDATE인 경우 전후 스냅샷이 모두 존재한다.
2. 배열의 각 컬럼이 실제로 다른 값을 가진다.
3. 실제로 달라진 감사 대상 컬럼이 배열에서 누락되지 않는다.
4. 배열 원소가 중복되지 않는다.
5. CREATE·DELETE의 전후 스냅샷 NULL 규칙과 모순되지 않는다.

저장 후 일반 UPDATE는 허용하지 않는다. 감사 오류가 발견되면 원본 배열을 수정하지 않고 `AuditCorrection`으로 설명한다.

### 5.4 인덱스 방침

컬럼명별 감사 검색 요구가 실제로 생긴 경우에만 GIN 인덱스를 추가한다.

```sql
CREATE INDEX ix_change_record_changed_columns
    ON audit.change_record
    USING gin (changed_columns);
```

현재 요구사항에는 컬럼명 자체를 검색 조건으로 사용하는 업무가 없으므로 초기 구현에서는 이 인덱스를 생략할 수 있다.

## 6. 정규화 상태를 유지할 대상

### 6.1 변경분류(ChangeRecordCategory)

변경분류는 변경항목과 달리 감사 검색을 위한 독립 분류 차원이다. 수강 상태와 성적이 한 처리에서 함께 달라질 수 있고, 감사 화면에서는 두 변경을 구분하여 찾아야 한다.

따라서 다음 이유로 별도 자식 엔터티를 유지한다.

- 한 변경기록에 복수 분류가 붙을 수 있다.
- 분류 코드를 기준으로 여러 변경기록을 조회한다.
- `(category_code, change_record_id)` 인덱스로 감사 검색을 지원할 수 있다.
- 전후 JSONB를 매번 해석하지 않고 분류 조건을 적용할 수 있다.

다만 모든 변경기록에 최소 한 분류를 강제하려면 허용 코드와 부여 규칙을 별도로 확정해야 한다. 허용 코드가 확정되지 않으면 최소 카디널리티를 `0..N`으로 낮추고, 확정 후 `1..N`으로 올린다.

### 6.2 업무행위자와 행위자역할

복수 역할과 유효기간은 반복 가능한 독립 업무 사실이다. 역할 이력을 업무행위자 컬럼이나 배열로 합치면 역할별 시작·종료 시각과 처리 시점 권한을 검증하기 어려워지므로 현재 분리를 유지한다.

### 6.3 변경요청·변경승인·변경처리·변경기록

네 엔터티는 다음과 같이 발생 단위가 다르다.

| 엔터티 | 발생 단위 |
|---|---|
| 변경요청 | 승인 대상 변경 제안 한 건 |
| 변경승인 | 요청에 대한 최종 승인·반려 판단 한 건 |
| 변경처리 | 함께 성공하거나 실패하는 실제 업무 트랜잭션 한 번 |
| 변경기록 | 한 처리에서 변경된 학사 대상 한 건 |

요청은 처리 없이 취소·반려·오래됨으로 끝날 수 있고, 승인 불필요 처리는 요청 없이 발생할 수 있으며, 한 처리는 여러 변경기록을 가진다. 합치면 NULL 속성과 반복 그룹이 늘고 승인 전 데이터와 실제 변경 데이터의 경계가 사라지므로 현재 분리를 유지한다.

### 6.4 보존정책·보존보류·폐기실행

보존정책은 반복 사용되는 정책 버전, 보존보류는 특정 분쟁·감사 범위에 대한 예외 조치, 폐기실행은 승인받은 실제 작업 증적이다. 세 대상은 발생 시점·책임자·상태·보존 목적이 다르므로 통합하지 않는다.

### 6.5 고정 코드값

다음 값은 별도 코드 엔터티로 분리하지 않는다.

- 학생 학적 상태
- 교수 재직 상태
- 강좌 개설 상태
- 수강 상태
- 성적
- 행위자 종류와 역할 코드
- 요청·승인·실행 상태
- 변경 처리 종류와 변경분류 코드

이 값들은 사용자가 지속적으로 등록·수정하는 독립 마스터가 아니며 허용 집합이 작고 안정적이다. PostgreSQL CHECK 제약 또는 제한된 코드 도메인으로 관리한다. 코드명, 다국어 표시명, 적용기간 등을 독립적으로 관리해야 하는 요구가 생길 때만 코드 엔터티 분리를 재검토한다.

## 7. 유지할 의도적 비정규화

### 7.1 행위자 코드·표시명 스냅샷

승인·처리·조회 당시의 담당자 정보를 재구성해야 하므로 현재 `AuditActor`의 코드·표시명과 별도로 사건 시점 스냅샷을 유지한다. 현재 행위자의 표시명이 변경되더라도 과거 사건의 표시값은 바뀌지 않아야 한다.

일관성은 사건 생성 프로시저가 행위자에서 값을 복사하고 이후 스냅샷 UPDATE를 금지하는 방식으로 보장한다.

### 7.2 업무 대상의 전후 JSONB 스냅샷

학과·학생·교수·교과목·강좌·수강은 속성 구조가 서로 다르고, 현재 학사 행이 삭제된 뒤에도 전체 내용을 재구성해야 한다. 대상 유형별 자식 스냅샷 테이블을 추가하면 엔터티와 관계가 크게 늘어나므로 JSONB를 유지한다.

JSONB는 다음 방식으로 통제한다.

- `target_type`별 허용 구조와 필수 키를 정의한다.
- `snapshot_schema_version`을 함께 저장한다.
- 신뢰된 생성 함수만 스냅샷을 만든다.
- 현재 학사 행과 FK로 연결하지 않는다.
- 생성 후 수정하지 않는다.

### 7.3 학생·강좌 검색 태그

`student_number_tag`와 강좌키 태그 네 개는 `business_key_snapshot`에서 계산할 수 있지만, 특정 학생·강좌의 변경 흐름을 정형 인덱스로 검색하기 위해 유지한다.

태그는 스냅샷 생성 함수가 업무키 스냅샷과 동시에 생성하며, 대상 유형별 필수 태그 조합을 검증한다.

### 7.4 변경 중요도 요약값

`ChangeOperation.is_important`는 변경분류와 전후값에서 계산 가능하지만 중요 변경 목록을 처리 단위로 빠르게 조회하기 위해 유지한다. 같은 트랜잭션에서 자식 변경기록·분류로부터 계산하며 사용자 입력을 허용하지 않는다.

### 7.5 폐기 건수 요약값

`DisposalExecution.deleted_record_count`는 실행 결과의 대표 집계값으로 유지한다. 폐기 프로시저가 실제 성공 건수로 생성하고 `result_snapshot`과 모순되지 않는지 종료 시 검증한다.

## 8. 비정규화하지 않을 항목

다음 중복값은 추가하지 않는다.

- 학생·교수 테이블의 학과명
- 강좌 테이블의 교과목명·교수명
- 수강 테이블의 학생명·교과목명·현재 수강 인원
- 학년 안내 문구, `미등록`, `미정`
- 정원에서 계산 가능한 잔여석
- 입학일에서 계산 가능한 입학 연도
- 승인 관계를 우회하는 승인 여부 불리언

현재값 조회로 안전하게 계산할 수 있고 과거 시점 사실도 아닌 값은 중복 저장하지 않는다.

## 9. 종합 모델 반영 기준

### 9.1 엔터티·속성 문서

`erd-03-03-refined-entities-attributes.md`에는 다음 결론을 반영한다.

- `ChangeRecord`에 `changed_columns TEXT[]`를 추가한다.

### 9.2 관계·카디널리티 문서

`erd-04-to-05-relationships-cardinality.md`는 정제된 모델을 기준으로 다음과 같이 작성한다.

- 변경기록–변경분류 관계를 U-R18로 정의한다.
- 감사 물리 관계 수를 19개에서 18개로 변경한다.
- 전체 물리 관계 수를 25개에서 24개로 변경한다.
- UPDATE 변경기록의 최소 변경항목 보장 설명을 배열 검증으로 바꾼다.
- 변경항목 자식 우선 폐기 설명을 제거한다.

## 10. 검증 시나리오

제안 적용 후 다음 시험을 통과해야 한다.

1. UPDATE 변경기록에서 빈 `changed_columns`를 저장하려 하면 실패한다.
2. 실제로 값이 같은 컬럼은 `changed_columns`에 포함되지 않는다.
3. 실제로 값이 다른 컬럼이 배열에서 누락되면 감사 생성이 실패한다.
4. 배열에 같은 컬럼명이 중복되면 실패한다.
5. 허용되지 않은 컬럼명이 포함되면 실패한다.
6. CREATE·DELETE 기록은 빈 배열을 저장할 수 있다.
7. 감사기록 생성 후 배열을 직접 수정하려 하면 권한 또는 트리거로 거부된다.
8. 학생·강좌 검색 태그가 업무키 스냅샷과 일치한다.
9. `is_important`가 변경분류·전후값과 일치한다.
10. 변경분류가 두 개인 기록을 각 분류 조건으로 모두 조회할 수 있다.
11. 폐기 시 별도 변경항목 자식 삭제 없이 변경기록 보존 단위를 처리할 수 있다.

## 11. 재검토 조건

다음 요구가 추가되면 `ChangeRecordColumn`의 별도 엔터티 복원을 검토한다.

- 컬럼별 이전값·이후값·보정 설명·민감도 등 독립 속성을 저장해야 한다.
- 컬럼 단위 접근 통제 또는 마스킹 정책이 필요하다.
- 컬럼별 변경 횟수 통계가 핵심 업무가 된다.
- 다른 엔터티가 특정 변경항목 한 건을 직접 참조해야 한다.
- 배열 GIN 인덱스로 감당하기 어려운 컬럼 단위 검색량이 확인된다.

요구가 아니라 추측만으로 엔터티를 다시 추가하지 않는다. 실제 조회·무결성·보존 요구와 시험 근거가 있을 때 재정규화한다.

## 12. 최종 제안

1. 학사관리 6개 엔터티와 주요 감사 업무 엔터티의 현재 분리는 유지한다.
2. `ChangeRecordColumn`은 독립 업무 사실이 아니므로 제거하고 `ChangeRecord.changed_columns TEXT[]`로 통합한다.
3. `ChangeRecordCategory`는 복수 감사 분류 검색을 위해 유지한다.
4. JSONB 스냅샷, 행위자 스냅샷, 검색 태그와 요약값은 생성 책임과 검증 규칙을 전제로 유지한다.
5. 고정 코드값을 별도 코드 엔터티로 추가하지 않는다.
6. 종합 결론을 엔터티·관계·DBML·DDL·검증 문서에 일관되게 반영한다.

이 제안은 3NF를 무조건 완화하는 것이 아니라, 독립 업무 의미가 없는 변경 컬럼 목록만 통제된 다중값 속성으로 되돌리는 제한적 비정규화다. 감사 원본은 전후 스냅샷이며 배열은 조회·표시를 위한 보조값이라는 우선순위를 유지한다.
