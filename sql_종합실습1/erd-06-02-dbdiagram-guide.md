## 2. 작업계획

1. 정제된 18개 엔터티와 모든 속성을 PostgreSQL DBML로 변환한다.
2. PK, 후보키, 복합 유일 제약, 주요 CHECK와 검색 인덱스를 표시한다.
3. 24개 물리 관계에 A-R01~A-R06과 U-R01~U-R18 식별자를 부여한다.
4. 학사와 감사 영역을 색상과 TableGroup으로 구분한다.
5. 물리 FK가 없는 스냅샷·다형 관계와 절차상 최소 카디널리티를 범례로 분리한다.
6. dbdiagram에 붙여 넣은 뒤 그룹 단위로 배치하고 선 겹침을 최종 조정한다.

## 3. 결과물 구성

| 구분 | 수량 | 표현 방식 |
|---|---:|---|
| `academic` 엔터티 | 6 | 파란색 테이블 헤더, `academic_core` 그룹 |
| `audit` 엔터티 | 12 | 보라색 테이블 헤더, 업무별 4개 그룹 |
| 물리 관계 | 24 | DBML `Ref`, DELETE/UPDATE RESTRICT |
| 논리 관계 | 7 | 관계선 없이 `logical_relationships` 주석 |
| 절차상 최소 카디널리티 | 4 | `procedural_cardinality_rules` 주석 |

## 4. 범례

| 표기 | 의미 |
|---|---|
| 파란색 헤더 | `academic` 스키마 |
| 보라색 헤더 | `audit` 스키마 |
| 실선 관계 | 물리 FK |
| nullable FK | 자식 한 건이 부모를 `0..1`건 참조 |
| `unique` FK | 부모 기준 최대 한 자식만 연결 |
| JSONB·검색 태그 | 학사 대상과의 논리 연결이며 물리 FK 없음 |
| 테이블 Note | DBML 선만으로 표현하지 못하는 최소 참여 수 또는 보존 규칙 |

모든 물리 FK는 자식 PK에 포함되지 않는 비식별 관계이며 `ON DELETE RESTRICT`, `ON UPDATE RESTRICT`를 적용한다.

## 5. dbdiagram 사용 방법

1. dbdiagram.io에서 새 다이어그램을 연다.
2. DBML 편집기의 기본 내용을 모두 지운다.
3. `erd-06-01-dbdiagram.dbml` 전체를 붙여 넣는다.
4. 다이어그램이 생성되면 `academic` 그룹은 왼쪽, `audit` 그룹은 오른쪽에 둔다.
5. `audit_identity`를 중앙 상단에 두고 행위자에서 뻗는 관계선을 짧게 만든다.
6. `audit_change`는 요청 → 승인/처리 → 기록 → 분류 순으로 배치한다.
7. `audit_retention`은 오른쪽 하단, `audit_observation`은 오른쪽 상단에 둔다.
8. 세 개의 범례 Note는 테이블 영역 바깥쪽에 배치한다.
9. 필요하면 세부 좌표를 조정한 뒤 PNG 또는 PDF로 내보낸다.

DBML 파일은 테이블 그룹을 정의하지만 각 테이블의 캔버스 좌표까지 고정하지는 않는다. 실제 dbdiagram 렌더링에서 테이블과 관계선이 정상 생성되고 주요 테이블을 가리는 선이 없음을 확인했다. 사용 화면 크기나 내보내기 비율에 따라 세부 좌표는 추가로 조정할 수 있다.

## 6. DBML 표현과 구현 제약의 구분

### 6.1 DBML에 직접 반영한 항목

- 18개 엔터티의 PK, 필수·선택 속성 및 PostgreSQL 타입
- 코드 도메인의 Enum
- 단일·복합 후보키와 주요 검색 인덱스
- 24개 물리 FK와 참조 동작
- 행 상태에 따른 주요 다중 컬럼 CHECK
- 학사·감사 스키마 및 시각 그룹

### 6.2 프로시저·트리거로 보장할 항목

- 업무행위자 생성 시 역할 이력 최소 1건
- 변경처리 생성 시 변경기록 최소 1건
- UPDATE 변경기록 생성 시 `changed_columns` 최소 1개와 전후 스냅샷 일치
- 모든 변경기록 생성 시 변경분류 최소 1건
- 승인자의 유효 역할과 자기 승인 금지
- 정원 초과 방지를 위한 동시성 제어
- 스냅샷 JSON 구조와 검색 태그의 일치
- 보존기간·활성 보존보류를 고려한 폐기 가능 여부
